### Added

- **plan-agent `finalize-plan` reconciles the plan against what shipped (9.11.0)** — Steps 3a–3c only ever asked one direction of the question — *was each planned thing built?* — so a plan whose implementation grew a file, a flag, or a different approach was marked completed while its published artifact still described the scope imagined before the work started. New Step 3d asks the other direction: it takes the commits that touched the spec (`git log --follow`, falling back to the default-branch range when the spec commit has not landed), excludes housekeeping paths, and sorts the rest against `## Files` and the 3a tokens into **shipped but unplanned** and **built differently**. Both buckets are reported in Step 4 before you confirm. `5c2` writes unplanned work into `## Steps` as an already-done `Unplanned:` step (under a trailing `### Phase: Unplanned` in a phased spec, so 5a0's completable-versus-checkpointed gate is not muddied), and `5d2` writes a changed approach into `## Decisions` rather than the `## Completion Report`, whose entries all render as defects. No renderer change — every bucket routes to a section `build-plan-html.mjs` already parses (#613)
- **git-agent `ship-autonomous` context guard (4.20.0)** — The pipeline derives every input from `git` and `gh`, but Step 5 ends the turn and waits, so each PR event that wakes the session re-sends the whole transcript as input — a pipeline that needs none of that context pays for all of it, once per CI event. New Step 0 checks whether the session is already long and offers three routes: `clear` (**STOP** — you run `/clear` and re-invoke, because a skill cannot clear its own context), `background` (dispatch `ship-bg` then `ship-ci-bg`, each subagent getting a fresh context window; merge still returns to the foreground, since a subagent has no user to ask for approval), or `continue`. Skipped on a short session, so it catches an expensive default rather than adding a prompt to every run. Detail lives in `references/context-guard.md`; the former Step 0 (`ExitPlanMode`) is now Step 0.5 (#608)
- **plan-agent `publish-hub` (9.8.0)** — Bundles a plan and its related HTML — the `prototype:` file, any `--extra` pages, `design:` as an external-link tab — into one self-contained tabbed hub page and publishes it to a stable URL recorded as `hub-artifact-url:`, never touching the plan's own `artifact-url:`. Each document is isolated whole in an `<iframe srcdoc>` panel; output is capped at 15 MB (under the 16 MB artifact limit) and on overflow the bundler exits 1 naming the largest embedded document. `scripts/build-plan-hub.mjs` + `bin/plan-agent-hub`, pinned by `tests/plugins/test-build-plan-hub.mjs` (#603)
- **plan-agent design phase (9.5.0)** — `/plan-agent:design` turns a plan, one-line idea, image, or Figma URL into a multi-artboard design canvas, deriving one artboard per user-facing step and delegating authoring and publishing to Claude Code's built-in `design` skill. Working artboards land under `docs/designs/<plan-slug>/`; the published canvas URL and that directory are written back as `design:` and `design-dir:`, giving the plan a **View design** header link and `build` a visual spec to read. Ships a designs gallery (`build-designs-index`) and a drift check (`check-design-drift`) that reuses the same UI-signal filter the skill derives artboards from, so hook and skill never disagree (#596)
- **code-testing-agent `verified-change` (3.6.0)** — Changes working code under a local merge gate: runs `bash scripts/verify.sh` once before touching anything so a pre-existing failure is not mistaken for yours, writes the regression assertion first and mutation-checks it (a test that survives its own mutation is rejected and rewritten), then loops the gate up to 8 times and emits a VERIFICATION section recording what actually ran. Bundles `scripts/verify.sh` and `install-verify-gate` for repos with no gate of their own (#594)
- **Local merge gate for this repo** — `scripts/verify.sh` and a `## Merge gate` rule in `CLAUDE.md`: no merge is proposed until the gate exits 0 on the machine and the PR body's VERIFICATION section records what was run. `SKIP (not configured)` is recorded as a skip, not a pass. GitHub Actions is frequently billing-blocked on this account, so red CI is not evidence of a defect and green CI is not evidence of correctness (#594)
- **How-to guides for every skill** — 12 Markdown files under `docs/guides/how-to/`, one per plugin, covering all 63 skills with a fixed four-part entry: the slash command and its `argument-hint`, the natural-language phrasing that triggers it, what actually happens, and the gotcha. The 12 skills carrying `disable-model-invocation: true` are marked command-only rather than given a phrase that would silently do nothing. Indexed from a new **How-To Guides** section in the root README
- **plan-agent 8.2.0 — product, security, and frontend plan reviewers** — `review-plan`'s Agent Team grows from seven to ten: `plan-reviewer-product` (user problem, scope sizing, falsifiable success criteria, rollout) and `plan-reviewer-security` (authn/authz, data handling, trust boundaries, secrets, dependency risk) join the core roster, and `plan-reviewer-frontend` (component boundaries, state placement, render cost, design-system fit) joins UX and accessibility behind the `ui_signals_present` gate. These are the three lenses that `product-plans` covered and no existing plan reviewer did

### Fixed

- **plan-agent header links render as chips; prototype refocus reaches a leading select (9.13.1)** — The `View prototype`, `Issue #N`, and `View design` anchors in `.plan-header-actions` carried no CSS, so in a flex row of explicitly ordered children they fell to `order: 0`, sat ahead of the status badge, and drew as bare underlined text. They now share the badges' chip rule and an `order` slot between the badges and the controls, and join the 44px touch-target list. Separately, the prototype skeleton's post-submit refocus used `form.querySelector('input')`, skipping a leading `<select>` or `<textarea>`; it now matches all three. Both measured in a browser and pinned by `tests/plugins/test-plan-header-links.mjs` and `test-prototype-refocus.mjs`
- **The prototype store stops handing `render()` shapes it cannot walk (plan-agent 9.13.2)** — `load()` in `PROTOTYPE-SKELETON.html` returned whatever `JSON.parse` produced from localStorage, and `JSON.parse` accepts `[null]`, `"x"`, `{}`, or `[[]]` without complaint: `[null]` and `"x"` threw an uncaught `TypeError` and left the table empty, `{}` showed the empty state with the summary badge counting `undefined`, and `[[]]` rendered a blank row. A new `isRecordList()` inside the extractable STORE block accepts only an array of non-null, non-array objects; anything else falls back to the seed, and a stored `[]` still loads as an empty list
- **A stalled pre-PR reviewer no longer stalls the ship (git-agent 4.20.2, code-review 3.3.6)** — `agent-code-reviewer` ran out of its ten turns or stalled before reporting in three 2026-09-03 sessions, and pr-agent Step 4.7 / ship Step 4.5 had no rule for a missing report, so the ship hung until the user re-sent the command. The agent's cap is now 30 (a diff review spends a turn per file it reads), and both dispatch sites treat a partial, empty, or `### Summary`-less result as "no report" and run the same checklist inline, saying so in the PR body or step report instead of re-dispatching (#619)
- **Fresh-machine install steps and false exec-bit failures (settings-sync 1.1.5)** — A fresh-machine restore ended in a "point me at your backup folder" request: the plugin README and every how-to guide gave only `/plugin install settings-sync@agentics-kit`, which fails until `/plugin marketplace add shawn-sandy/agentics` has run, so both now lead with the marketplace step. `settings-restore` Step 7 checked hooks with a blanket `find ... ! -perm -u+x`, so a hook run as `python3 hook.py` — never executable anywhere — was a `FAILED` entry and a correct restore was reported INCOMPLETE; the check now lists what is executable in the backup (`find -L`, so symlinked hooks count) and reports only those not executable locally. `settings-backup` Step 5 lists repo-root entries that are neither a target nor a control file and Step 8 reports them under `Not a backup target (left in repo)` — a stale `plans/` had sat in a real backup for six weeks and would have returned on every new machine; nothing is deleted. Pinned by `tests/plugins/test-settings-restore-exec-bits.sh` and `test-settings-backup-stale-entries.sh` (#618)
- **The local merge gate passes on machines with ruff installed (#616)** — `tests/plugins/test-lint-before-commit.sh` built its flake8-fallback case by prefixing a fake-flake8 directory onto `PATH`, so a real `ruff` behind it won the lookup, linted the empty fixture clean, and the case failed on any machine with ruff — which made `scripts/verify.sh` unsatisfiable on unrelated work. The case now runs under a replaced `PATH` (`fire_with_only_path`) with flake8 genuinely present and ruff genuinely absent, and pins that the helper restores `PATH` afterwards. No hook change — `lint-before-commit.py` was correct all along
- **Artifact-published plans reach review, design, and prototype (plan-agent 9.10.0)** — Since 9.7.0 the ordinary shape of a plan on disk is a `.md` spec carrying `artifact-url:` and nothing else, and three consumers still assumed a file. `review-plan` discovered plans with `glob docs/plans/*.html`, so running it bare did not fail — it silently reviewed the most recent *file*-published plan instead, the worse outcome; discovery now unions that glob with the same frontmatter-bounded spec scan `finalize-plan --all` uses, and accepts an explicit `.md` path. Step 7 no longer resurrects the sibling the author chose not to publish: it records *where* the plan lives as a finding separate from the edit mode, then overwrites the sibling when one exists and otherwise renders to the scratchpad and republishes to the recorded URL (`Artifact` joins the skill's `allowed-tools` and the `agent-review-plan` subagent's `tools`, without which background mode would silently never republish). `design` and `prototype` tested for `.html` only, so a `.md` fell through to their raw-idea branch and the skill ran to completion having designed against a filename — both now classify `.html` or `.md` as a plan path (#609)
- **The build completion gate stops failing artifact-only plans (plan-agent 9.10.1)** — `skills/build/references/completion-gates.md` Step 5.3 hardcoded `--check -o "<stem>.html"`, a file an artifact-delivered plan does not have, so such a plan reported `html FAIL` on a spec whose `steps` and `criteria` rows both passed — and the failure's remediation line named the one command `references/re-render.md` forbids, since writing the sibling flips the plan's gallery card off the shared artifact onto a local path. `finalize-plan`'s `references/write-completions.md` already carried the carve-out; the two had drifted. `scripts/build-plan-html.mjs` also now creates missing `-o` parent directories: both references document the artifact re-render as `-o "$SCRATCHPAD/<stem>.html"` and `<stem>` always carries directories, so the documented command died on an unhandled `ENOENT` before writing a byte. `--check` still writes nothing, directories included (#610)
- **A zero-byte CI log no longer reports as "CI never dispatched" (git-agent 4.20.1)** — The 4.19.4 rule treated three states as a non-dispatch, and the third — every job failed *and* `--log-failed` returned zero bytes — was an extrapolation its cited measurement never covered: all four blocked runs in the 2026-08-14 window had an **empty `jobs` array**, so the zero-byte log was never observed independently of it. A dispatched run can return no log bytes from expired retention, a fetch landing on a different attempt, or a transient API error, and calling that a billing block tells you to ignore a real failure. `merge` and `ship-autonomous/references/ci-autofix.md` now treat an empty run list or empty `jobs` array as the whole test — verified against live runs, a non-empty `jobs` array carries `startedAt` and populated `steps` and is proof of dispatch on its own — and report a started-jobs run with an unreadable log as **"CI failed — logs unavailable"**, named down to the failing job and step. Both files also now bind the run they classify to the PR's head commit (`--commit <headRefOid>`): `merge` listed by `--branch`, which returns every recent run across every commit and workflow on the branch, and `ci-autofix.md` used a bare `gh run list | head -1` unfiltered across the **whole repository**, so a concurrent PR's red run could be autofixed against (#607)
- **plan-agent's own hook count was wrong in three files (9.10.2)** — The plugin README said `dispatch` "fans out to the six below" and listed six children while `dispatch.py` spawns seven (`render-plan-html` was missing), putting it in conflict with the root README's "all seven Write/Edit hooks"; `dispatch.py`'s module docstring said "six" while the parenthetical beside it enumerated seven; and the same README cell called `dispatch` "the plugin's only registered hook" when `hooks.json` registers two `PostToolUse` entries — it is the only registered *Write/Edit* hook. The root README's how-to table summed to 66 skills under a line that said 65; the table is the correct side (#612)
- **Completion state reaches artifact-published plans (plan-agent 9.9.0)** — A plan published to claude.ai is a spec carrying `artifact-url:` with no sibling `<stem>.html`, and that missing sibling is the same signal `render-plan-html.py` uses to skip re-rendering. `plan-status` wrote `status:` into the frontmatter and stopped, so the spec read `completed` while the page everyone else opened still read `todo`. It now renders to the scratchpad and republishes to the recorded URL, carrying the whole spec — step markers, `- [x]` criteria, and Completion Report — and bulk mode reports `republished: N`. `finalize-plan --all` gained a spec-side scan so artifact plans are sweep candidates at all, guarded by frontmatter-bounded matching (a completed plan documenting plan-agent's own keys was becoming a candidate off a `status: todo` line in its body), a `# Plan:` heading gate, and a host requirement on the URL. Delivery sends the `.md` and the artifact URL rather than promising a `<stem>.html` that does not exist (#604)
- **The review workflow re-fired on every push, so fixing a finding manufactured new findings** (`.github/workflows/claude-code-review.yml`) — `on.pull_request.types` included `synchronize`, which fires on every push to a PR branch. Each fix pushed in response to a bot comment therefore triggered a fresh full review from all three subscribed reviewers, whose new comments prompted another fix, another push, another round. Measured over 2026-07-12 → 2026-08-12 across this repo and five others: **332 PRs drew 2,001 reviews**, mean 6.0 per PR, max 38; 91 PRs took 8 or more. 110 of those reviews were submitted *after* an approving verdict was already on the PR. The step change is sharp and behavioural rather than mechanical — reply rate to bot findings sat at 0.25–0.35 through late July, then hit 1.01 in the week of 2026-07-27 and has stayed near 1.00 since, while findings per PR barely moved (3.2 → 3.9) and median PR size barely moved (394 → 439 lines). Nothing in configuration explains it: this workflow file had not been touched since 2026-02-24. `synchronize` is now dropped, so the review fires once when a PR opens; `ready_for_review` is retained, which makes draft → ready an explicit re-review request rather than an automatic one. Worth noting what this does **not** fix: `copilot-pull-request-reviewer` and `chatgpt-codex-connector` posted 808 of those 2,001 reviews and have never once returned a blocking verdict between them — `coderabbitai` holds all 67 `CHANGES_REQUESTED` and 101 of the 104 approvals. Disabling those two is a repository setting, not a file in this repo
- **Eight more documented Bash commands could never run, across five plugins (skill-reviewer 2.5.0, wcag-compliance-reviewer 1.4.0, social-media-tools 2.22.0, artifact-tools 1.11.0, git-agent 4.11.0)** — the same defect 8.3.0 fixed in `plan-agent`, everywhere else it survived. Each spelled a Bash command containing `${CLAUDE_PLUGIN_ROOT}`, which the Bash tool refuses with `error: Contains expansion` before permission rules are consulted, and which is not exported into that tool's environment anyway. Each now ships a `bin/` wrapper invoked by bare name: `skill-reviewer-scan-tools`, `skill-reviewer-measure-description`, `wcag-check`, `social-export-session`, `artifact-export-session`, `git-agent-extract-plan-issues`. Wrappers are plugin-prefixed because `bin/` entries from all enabled plugins share one `PATH`, and `social-media-tools` and `artifact-tools` both bundle a script named `export_session.py`. **An eighth site was found beyond the seven known:** `skill-reviewer`'s `/check-description` invoked `"${CLAUDE_PLUGIN_ROOT}/scripts/measure-description.sh"` with no interpreter prefix, making it invisible to a `node|python3|bash` scan — the new test carries a second, command-position pattern for that shape. Worth noting `wcag-compliance-reviewer` 1.3.1 shipped this defect *while claiming to fix it*, under the heading "The documented checker command actually runs": it traded a command that worked from one directory for one that worked from none. New repo-wide guard `tests/plugins/test-no-shell-expansion.sh` is wired into CI; all seven of its checks were mutation-tested, which caught three of them passing vacuously — one off a comment, one off explanatory prose, and one whose error flag was set inside a command substitution and could never reach the caller. It defers `plan-agent` to `test-extractor-wiring.sh` rather than keeping a second ledger, and asserts that handoff so deleting either ledger fails loudly instead of leaving a plugin unguarded. **Not fixed here:** seven sites in `memory-tools` and `social-media-tools` remain ledgered, and `wcag-compliance-reviewer`'s `skills/` tree is synced from [shawn-sandy/skills](https://github.com/shawn-sandy/skills), so that half of the fix reverts on the next sync unless mirrored upstream
- **`plan-agent`'s plan renderer could not be invoked by any installed user (8.3.0)** — the four call sites 8.2.1 ledgered as known-broken are fixed, including `implementation-plan`'s render command, the plugin's most-used script. They all spelled a Bash command as `node "${CLAUDE_PLUGIN_ROOT}/…"`, which the Bash tool refuses with `error: Contains expansion` before permission rules are consulted; the defect runs deeper than that guard, because **`CLAUDE_PLUGIN_ROOT` is not exported into the Bash tool's environment at all** — it is a config-file substitution the harness applies to `hooks.json`, MCP/LSP, and monitor commands, so even without the refusal the path would have expanded to a bare `/scripts/…`. The general answer, and the one this fix uses: **a plugin's `bin/` directory is added to the Bash tool's `PATH`**, so bundled scripts are invokable as bare commands with no path, no `${VAR}`, and no environment dependency. `plan-agent` now ships `bin/plan-agent-render` and `bin/plan-agent-prototypes-index`, and `build-dist.mjs`'s KEEP allowlist gained `bin` so they actually reach published installs. Check 9 of `test-extractor-wiring.sh` now scans every model-facing markdown file (`skills/`, `agents/`, `commands/`) minus whatever check 10 ledgers, so the four repaired files are guarded against regressing; two new checks assert the wrappers run and that `bin` survives the dist build. **The ledger does not empty here** — it listed 8 sites across 6 files, and the 2 remaining (`plans-library`, `plans-open`) are a different defect class: inline heredoc snippets whose shell variables are set in the same block, which need extracting into real scripts rather than a `bin/` wrapper. That is the gallery pipeline's own change
- **`plan-agent` reviewers documented an extractor command that cannot execute (8.2.1)** — 8.1.1 (below) anchored all 15 extractor call sites to `${CLAUDE_PLUGIN_ROOT}` to fix a cwd-relative path bug. That spelling is right for a `Read` tool path and fatal for a Bash command: **Claude Code's Bash tool refuses any command whose text contains `${VAR}` or `$VAR` with `error: Contains expansion`**, since it cannot statically resolve the expansion — and the refusal fires *before* permission rules are consulted. Verified against 2.1.220: the command is unrunnable for an agent holding unrestricted `Bash`, and stays unrunnable with a matching `--allowedTools` rule. So 8.1.1 swapped one silent fallback for another. No `tools:` grant could have rescued it either: a prefix rule like `Bash(node "${CLAUDE_PLUGIN_ROOT}/…":*)` can never match (the guard rejects the command before matching), and a literal-path grant cannot ship because the install path varies per machine. All ten reviewer briefs and all ten `plan-reviewer-*` agent defs now instruct a plain `Read` of the plan HTML — what every review has actually been doing all along. This does **not** recover the ~10x per-reviewer token saving; it deletes a claim that was never true in practice. Separately, `Bash(git *)` *is* genuinely enforced for markdown-defined agents (`git status` runs, `node --version` is refused), so the read-only invariant itself was never breached. Eight further call sites across six files have the same defect — including `build-plan-html.mjs`, the plan renderer, `python3` heredocs in `plans-library`, and `realpath` calls in `plans-library` and `plans-open` — and are deliberately left unfixed here as a separate change; check 10 of `test-extractor-wiring.sh` ledgers them so the list can neither grow nor quietly shrink. Checks 5, 6, and 9 of that suite had to be **inverted**, because they previously *required* the broken wiring
- **`plan-agent`'s spec extractor was never published (8.1.1)** — The plugin bundled `scripts/lib/plan-spec.mjs` but not `scripts/extract-plan-spec.mjs`, the CLI that imports it, so the shared library shipped orphaned and no installed user could run the compute-on-read spec path at all. All 15 live call sites — the 7 reviewer briefs, the 7 `plan-reviewer-*` agent defs, and `prototype` — also invoked a bare `node scripts/extract-plan-spec.mjs`, a cwd-relative path that only ever resolved inside this repo. The review team therefore fell back to reading full plan HTML on every run, at roughly an order of magnitude more tokens per reviewer per cycle than the README advertises, and nothing surfaced the degradation. The extractor is now vendored alongside `build-plan-html.mjs` and covered by the existing byte-identity parity check; every call site is anchored to `${CLAUDE_PLUGIN_ROOT}`. Generated plans are unchanged — they stay self-contained and reference the plan by path
- **Compiled Python bytecode was published (social-media-tools 2.21.1)** — `scripts/__pycache__/session_usage.cpython-311.pyc` was committed before `__pycache__/` reached `.gitignore`, so the rule never applied and the file shipped in every install. It was inert (both its recorded source mtime and its interpreter magic number mismatched, so Python always discarded it) but it was dead weight in the package. Untracking it was not sufficient on its own: `build-dist` walks the **working tree**, not git, so `.gitignore` never filtered it — the builder's denylist covered only `.DS_Store` and a few siblings. `__pycache__/` and `*.pyc` are now `DROP_PATTERNS` entries, so the existing `build-dist --check` step fails if bytecode reappears. Worth noting the general shape: the marketplace's `git-subdir` path and the `build-dist --publish` mirror filter differently, and a file can reach one but not the other
- **`check_wcag.py`'s documented command could not run (wcag-compliance-reviewer 1.3.1)** — The skill and README both said `python scripts/check_wcag.py <file>`, which fails on two counts: the path is cwd-relative (the script lives at `skills/wcag-compliance-reviewer/scripts/check_wcag.py`), and `python` does not exist on a python3-only machine. Both call sites now use `python3 "${CLAUDE_PLUGIN_ROOT}/…"`. Note that `skills/wcag-compliance-reviewer/` is synced from [shawn-sandy/skills](https://github.com/shawn-sandy/skills), so that half of the fix needs mirroring upstream or the next sync reverts it
- **Unanchored `.gitignore` rules could silently unpublish plugin content** — Plugins ship via `git-subdir`, so git is the publish filter: any path under `kit/plugins/` matched by `.gitignore` is absent from the installed package, and `build-dist` still reports `0 dropped` because git never showed it the files. The loss is invisible from both ends. This already happened once — an unanchored `build/` swallowed `kit/plugins/plan-agent/skills/build/` — but `examples/`, `dist/`, `tmp/`, `temp/`, `logs/`, `coverage/`, and `.nyc_output/` were left matching at any depth, and `examples/` in particular is a plausible plugin directory name. All seven are now anchored to root. `node_modules/`, `__pycache__/`, and `*.pyc` stay unanchored deliberately — they are generated at arbitrary depth (python hooks run *inside* `kit/plugins/` and drop `__pycache__` beside themselves) and are never publishable content. No file was being swallowed at the time of the fix
- **Removed-plugins list drift** — The de-registered plugin list is written twice and had drifted in both directions: `issue-agent` was in `marketplace.json`'s `removed` array but missing from `.claude/rules/removed-plugins.md`, and `plan-interview` was the reverse. The rule file is the copy that matters — it loads unscoped in every session so the re-add confirmation gate fires before any plugin file is opened, so the missing `issue-agent` row was the gate with a hole in it for six weeks, not cosmetic drift. Both lists now hold the same eight names
- **`plan-hygiene.md` pointed at a deleted command** — The rule told you to run `/plan-hygiene` before committing, but that command left with the `plan-interview` plugin (removed 2026-07-17) and `plan-agent` never absorbed it. Replaced with the `verb-target` naming convention stated inline
- **Contradicting deferred-tool guidance** — `plugin-patterns.md` said *not* to explain the `ToolSearch` mechanic in skill bodies while `skill-authoring.md` supplied a verbatim block to paste; both load on `kit/plugins/**/skills/**`. No shipped skill carried the block and 41 carry the terse plan-mode guard, so `skill-authoring.md` was the stale side and its section is removed
- **Artifacts gallery merge conflicts** — `docs/artifacts/index.html` is now registered against the existing `plans-index` merge driver in `.gitattributes`, so two branches each saving an artifact no longer conflict on the regenerated index. Both galleries emit the same `<a class="gallery-card">` markup, so one driver serves both. The count patch also learned the artifacts gallery's `items` noun and now rewrites **every** rendered total rather than the first — both galleries print the count twice (a header and a `<span>` footer), and patching one left the page contradicting itself. Adds `tests/plugins/test-merge-gallery-index.sh`, wired into `check-plugin-versions.yml` — the first coverage either merge driver has had
- **HTML plans responsive layout** — Retrofit responsive CSS into every HTML plan and hardened the skeleton (plan-agent 2.4.1, #321); moved the PDF button and status badge below the title for responsiveness (#322); set pipeline-node padding to 1rem (#298)
- **CI version bump** — Reverted to direct-push version bump with ruleset bypass (#286)
- **`publish-dist` failure issues piled up** — The failure notifier titled every issue `publish-dist failed on <date>`, so each nightly run opened a fresh one and none closed on recovery: one recurring failure produced 20 open duplicates between 2026-07-15 and 2026-08-02. The title is now stable, a failure comments on the existing open issue instead of creating another, and a passing run closes it. Comments name the step that actually failed — the old body said only "the daily publish-dist workflow failed", which for a 12-gate fail-fast chain is the one detail that mattered. The open-issue lookup lists issues and filters on exact title rather than using `gh issue list --search`, whose index lags issue creation and would re-create the duplicates the fix removes (#403)
