## How it works

The `reference/SKELETON.html` is the single source every generated plan is filled from, so adding the goal prompt there ensures it appears in all future plans without further changes. The meta tag approach mirrors how the implement prompt (`plan-implement`) and workflow prompt (`plan-workflow`) are wired — a machine-readable declaration alongside visible UI.

The `.plan-goal` block uses `<details>` for progressive disclosure (collapsed by default) with a purple color scheme to visually distinguish it from the green implement row and blue workflow block. The `copyGoal()` function copies the goal text to the clipboard, matching the pattern of `copyWorkflow()`.

The key design decision is that the goal prompt is _always_ present — no flag, no complexity heuristic, no opt-in. The goal prompt frames the plan's outcome rather than its steps, so every plan benefits from having both: the implement prompt for step-by-step execution and the goal prompt for outcome-oriented latitude.

The `implementation-plan` SKILL.md was updated so Claude computes `{goal-prompt}` in Step 2 on every plan generation and fills the SKELETON's placeholder. The contract change and DOM order (`implement → goal → workflow`) are both asserted by `test-goal-prompt.sh`.

## How to use it

The goal prompt appears automatically in every HTML plan generated by `/plan-agent:implementation-plan`. No flags or options are needed.

The purple "Pursue as goal" disclosure row appears between the implement (green) and workflow (blue) rows. Clicking "Copy" copies the goal prompt, which is phrased as:

> "Achieve this goal: [plan objective]. Use the plan as reference, but optimize for the outcome."

This gives implementers explicit permission to deviate from the plan steps when a better path to the same result exists.
