## How it works

Ship a portable `verify.sh` merge gate and a `verified-change` skill that enforces test-first, mutation-checked changes, then dogfood both into the agentics repo so no change here is proposed for merge without local proof.

GitHub Actions is frequently billing-blocked on this account. A quota-blocked run fails every job in seconds with no test output, which means red CI is not evidence of a defect and green CI is not evidence of correctness — it is evidence of nothing at all. Merge readiness has to be provable on the machine. The repo already has most of a local gate and does not know it. `tests/run-all.sh` auto-discovers every `tests/**/test-*.sh`, `test-*.mjs`, and `*.test.mjs` and runs them, so new tests need no wiring. What is missing is a single entry point that also covers the non-test gates (marketplace validation, the plugin version guard, README table freshness), and a discipline that makes running it non-optional. The second half of the problem is test quality, not test presence. A test written after the implementation can pass for the wrong reason and nobody finds out until production. The mutation check closes that: deliberately break the implementation, confirm the new test goes red, restore. A test that stays green through a mutation is not a test. This repo has no `package.json`, no `tsconfig`, no ESLint config, and no Playwright. A gate hardcoding typecheck/lint/unit/e2e would be three no-ops and one real stage here, so the script auto-detects instead — which is also what makes one file serve every project rather than needing a generator. `code-testing-agent` already ships `tdd-loop`, whose RED phase depends on the production code not existing yet. That shape does not fit a change to code that already works, which is the gap `verified-change` fills.

- Marketplace stage count — `tests/run-all.sh` is the auto-detected unit stage, so the marketplace block contributes three stages (marketplace validation, version guard, README freshness) rather than re-running the suite a second time as step 4's wording implied; step 13's "unit stage and the three marketplace stages" is what shipped. - shellcheck detection — gated on a `.shellcheckrc`, not on the binary being installed, so the gate does not turn red for everyone the day someone runs `brew install shellcheck`; this repo has no `.shellcheckrc`, so lint reports SKIP. - `bin/install-verify-gate` shape — it is a pure `exec` wrapper over `assets/install-verify-gate.sh`, because check 3 of `tests/plugins/test-no-shell-expansion.sh` parses every wrapper for an `exec <interp> "$(dirname "$0")/…"` line and fails a wrapper that carries logic of its own. - Re-entry marker escape — `tests/test-verify-gate.sh` invokes the gate through `env -u VERIFY_GATE_ACTIVE`, because that test itself runs under the gate whenever the unit stage is `tests/run-all.sh`; without the escape the marker would refuse the very invocation the test exists to make. It is the one site allowed to clear it, and check 2 asserts the marker still refuses everywhere else. - Project-local copy scope — `.claude/skills/verified-change/` is a whole-directory copy including `assets/`, since the acceptance criterion requires `diff -r` against the plugin directory to print nothing; that makes three copies of the gate, all held in lockstep by the parity test. - Version-guard verification method — `node scripts/check-plugin-versions.mjs` compares `origin/main...HEAD`, which is empty on an uncommitted branch and therefore passes vacuously; the 3.5.2 to 3.6.0 bump was verified by calling the script's exported `findViolations` against the real working-tree change set. The CLI form becomes meaningful once the work is committed. - Silent-failure bug found by the dogfood — proving the parity test fails on a forked gate showed it exiting non-zero with no message, because `diff | head | sed` under `set -e` killed the script before the report. Fixed with `|| true`; the proof is what caught it.
