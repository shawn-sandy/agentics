# Authoring a prompt to fix plan-completion tracking

## Summary

Ran `/plan-agent:write-prompt` to author a reusable AI prompt addressing a real
bug in this repo: implementation plans generated by `plan-agent` finish their
work but never get their `status` flipped to `completed`, so the plans gallery
misrepresents what has actually shipped.

The output is a **task**-type prompt saved to
[task-fix-plan-completion-tracking-2026-07-15.md](../../prompts/task-fix-plan-completion-tracking-2026-07-15.md).
It instructs a future Claude session to diagnose the root cause with file:line
citations, then produce an implementation plan via
`/plan-agent:implementation-plan` — deliberately stopping short of writing the
fix.

No code was changed. The session produced two files: the prompt and this recap.

## Decisions

**Investigate before prescribing a mechanism.** The user was offered four
options for where the fix should live (automatic hook, strengthened
`finalize-plan` skill, both, or investigate-first) and chose investigate-first.
The rationale is that `plan-agent` already ships a `finalize-plan` skill and a
`validate-plan-filename.py` hook — so the gap is not "nothing exists," it's
"something exists and doesn't fire." Picking a mechanism before knowing why the
existing one is silent would have been guessing.

**The deliverable is a plan, not code.** The user chose "implementation plan"
over "working code" or "diagnosis report." This keeps the fix reviewable before
it lands, which matters because the change touches a plugin that other people
have installed.

**All four failure modes are in scope, and the prompt forces them to be traded
off against each other.** The user selected every option: false completion,
noisy prompts, silent skip, and the plugin-user gap. The prompt turns this into
a constraint rather than a checklist — it explicitly says a recommendation that
solves one failure mode while worsening another is not a fix. This is the load-
bearing part of the prompt, because the obvious mechanisms trade directly
against each other: a hook that always fires solves silent skip and creates
noise; a hook that trusts the model's self-assessment solves noise and creates
false completions.

**Scope every change inside `kit/plugins/plan-agent/**`.** The plugin-user gap
is a structural problem, not a bug: anything relying on this repo's local
`.claude/settings.json` or the maintainer's `~/.claude/rules/plan-mode.md` never
reaches someone who installed `plan-agent` from the marketplace. The prompt
makes this a hard constraint with an explicit justification escape hatch.

**Dropped the `<example>` block from the task template.** The `write-prompt`
skill's task template includes an input/output example pair. For an
investigate-then-plan task, any example would have been fabricated, and worse,
it would have anchored the diagnosis toward a preconceived answer — the exact
failure the investigate-first decision was meant to avoid.

## Learnings

**A skill existing is not the same as a skill firing.** The core insight that
shaped the prompt: `finalize-plan` already does exactly what's needed
(per-criterion verification, status write). The bug is almost certainly in
*triggering*, not capability. The prompt's step 2 enumerates four candidate root
causes — description never matches, user must remember a command, plan path
unknown by end-of-session, rule lives in user-local config — and demands evidence
for each rather than intuition.

**The false-completion trap has a specific shape.** Step 5 of the prompt's
`<thinking>` block encodes the test that matters: can the mechanism know *which*
plan file is in play and *whether its acceptance criteria are actually met*,
without asking the model to self-attest? Anything that can't answer both will
mark plans complete that aren't. This is worth carrying into the investigation —
it's the question that eliminates most naive hook designs.

**Session transcripts from skill invocations are mostly skill text.** The
bundled `export_session.py` produced a 527-line file that is largely the
`write-prompt` SKILL.md echoed back as the "user" turn, with a slug derived from
the skill's base-directory line (`base-directory-for-this-skill-users`). When a
session is driven by a slash command, the extracted transcript is a poor recap
source — writing from live context produced something far more useful. The
extractor isn't wrong; it just can't tell instruction text from intent.

**Worktree transcript paths resolve fine here.** The skill warns that worktrees
can break the project-slug lookup. In this case the slug
(`-Users-shawnsandy-devbox-agentics--claude-worktrees-skills-dynamic-model-switch-21faf0`)
resolved directly and the newest `.jsonl` matched the live session ID, so the
documented fallback wasn't needed.
