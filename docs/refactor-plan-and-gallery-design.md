## How it works

The visual refresh in step 1 replaced the generic `system-ui` / `#2563eb` token set in `plan-shell.mjs`'s `CSS` export with a named palette organized into semantic roles (`--paper`, `--panel`, `--ink`, `--ink-2`, `--ink-3`, `--accent`, `--moss`, `--signal`, `--mono`, `--ui`, `--prose`). Every retired token was kept as an alias pointing at its replacement for the duration of the refactor, then removed in step 6. Both the `:root[data-theme="dark"]` block and a `@media (prefers-color-scheme: dark)` guard were added so the page responds to both the toggle and the OS setting — the OS setting wins unless the user has made an explicit choice.

Step 2 narrowed the back-compat test at `tests/plugins/test-build-plan-html.mjs` from a whole-document byte comparison to an `extractSections` deep-equal, allowing intentional markup changes while still catching any accidental change to the DOM contract the extractor and gallery generator rely on.

Step 3 added the theme toggle. A small inline script in `<head>` reads `localStorage` before the first paint — necessary because plans are opened directly from `file://` in many workflows and a wrong-theme flash is worse than no dark mode. The toggle button carries `aria-pressed`, a 44×44 px hit area, and is hidden from the print stylesheet.

Step 4 collapsed the double-abstract layout by changing `objectiveCard` to accept an optional `glanceHtml` argument and rendering the `<section class="plan-glance">` inside `<div id="objective">` rather than as a sibling. The `<details class="step-verify-toggle">` disclosure was replaced with a plain labeled block so `Verify:` text is always visible; `extractSections` was already reading from `class="verify-body"` regardless of wrapper, so the extractor contract was unchanged.

Step 5 added the step rail. Each `.step-card` received a numeric `id` (`id="step-1"`, `id="step-2"`, …), and `nav()` was extended to accept the step list and emit a `<ul class="rail-steps">` of `<a class="rail-step">` links alongside the existing section links. Below 900 px the list moves inside a `<details>` so mobile readers retain jump targets. The existing `progressBlock` output and `NAV_ENTRIES` id list were left untouched so progress JavaScript and its two assertions kept passing.

Step 6 fixed the scroll-spy (the observer previously only reacted to `isIntersecting` entries, leaving the last highlighted link active forever), deleted the three superseded selectors, removed the step 1 token aliases, and repointed every remaining selector at the final token names. With one nav entry the stale highlight had been invisible; with a link per step it would have been a persistent wrong "you are here" marker.

Steps 7 through 9 handled the byte-identical mirror requirement and the gallery rebuild. All three copies of the build script (`kit/plugins/plan-agent/hooks/build-index.sh`, `scripts/build-plans-index.sh`, `docs/plans/build-index.sh`) received the `data-month` attribute and in-progress-first sort, keeping identical checksums. Client-side JavaScript in `plans-gallery.html` inserts the In-flight separator and month headings from `data-month` values so the merge driver's card-splice logic never encounters non-card markup — the driver is unchanged, and `tests/plugins/test-merge-gallery-index.sh` required no edits.

## How to use it

The redesign is transparent to plan authors — no invocation syntax changed. To view the result, render any plan spec:

```bash
node scripts/build-plan-html.mjs docs/plans/<slug>.md -o /tmp/check.html
```

Open the file and use the theme toggle (top-right of the header) to switch between light and dark modes. The sidebar step rail lists all steps as jump targets; on narrow viewports they collapse into a `<details>` disclosure. The gallery at `docs/plans/index.html` shows in-flight plans first, and the search field and status segmented control filter live.
