The work started from a plain question: what does the build skill do when you give it no plan? It stops, and tells you to go run a different command. The session turned that dead end into a designed, reviewed proposal for walking the user through to a finished plan instead.

The finding that shaped everything came early. The pipeline this work needed already existed, wired in the opposite direction. The task was never “build a pipeline” — it was “let one skill enter the pipeline that is already there.” That reframing cut the estimated change from three files to roughly twenty-five lines in one.

Everything is committed as 3c37605. Nothing is implemented: the plan’s status is todo.

Decisions

Reuse the pipeline that already exists, rather than rebuilding it inside build.

The handoffs between the three skills are already wired. Re-implementing them would mean a new flag on a neighbouring skill plus a guard against infinite loops, spread across three files.

Rejectedbuild sequencing the stages itself (touches three files, duplicates existing logic); a fourth skill owning the pipeline (cleanest boundaries, but a whole new skill to avoid ~25 lines).
Ask once whether to start from a proposal.

The proposal skill handles a small, well-understood idea by just answering it — producing no document. Running it unconditionally would leave the chain holding nothing.

RejectedAlways running it and letting it scale itself down; skipping the proposal stage entirely.
Offer what the search found instead of silently adopting it.

Otherwise a forgotten plan sitting in the directory can quietly win over the goal the user just typed.

RejectedSkipping the search entirely (loses the ability to resume interrupted work); only chaining when the directory is completely empty (leaves the silent pickup in place).
“Not yet” ends the whole run, not just one step of it.

That prompt is the only place the user is asked whether to build. Treating it as declining just the inner step would build the thing they declined seconds earlier.

RejectedThe narrow reading, which the proposal originally documented; asking a second time on the way back.
Pin an explicit model on the skill that writes code.

Kept even after a reviewer argued against it, because the alternative is inheriting whatever the previous stage happened to set.

RejectedReverting to inherited; documenting the defect instead of fixing it. The reviewer’s cost and access objections are recorded as a known tradeoff rather than acted on.
Write the new tests scoped to the section they guard.

The existing test file documents, in its own comments, a whole-file search passing against a change that deleted all five rules it was supposed to protect.

RejectedWhole-file searches (demonstrably weaker); a structural parser heavier than anything else in the test suite.
Release this as a major version, not a minor one.

The repository’s own rule classifies changes to how a command accepts input as major. The automated check only enforces “newer than the main branch,” so it would never have caught the undersized bump.

RejectedMinor, as originally written into the plan.
Reach the new behaviour only through the explicit command.

The goal becomes a parameter you pass, not a phrase that triggers the skill. This removes an entire class of false matches instead of trying to word around it.

RejectedA narrow automatic trigger for phrasing that sounds like creating something; a wide trigger that asks a clarifying question at runtime.

Learnings

  • A model override does not unwind when a skill finishes.It applies for the rest of the turn, so in a chained run the stage that writes code inherits whichever model the last planning stage declared — not one anyone chose. Found by reading the reference rather than assuming.
  • The repository’s only comparable pipeline chose the opposite approach.The autonomous shipping skill declares the delegation tool and then never uses it, reimplementing every stage inline. That is a real argument against the approach taken here, and it is recorded rather than explained away.
  • Choice prompts cap at four options.The unbounded “which plan did you mean?” offer could not have displayed at all in this repository, which holds a dozen candidates. The design had specified a prompt the interface cannot render.
  • A matching problem can be deleted instead of solved.Rather than scoring existing plans against the user’s goal, the fix was noticing that a stated goal and a “did you mean?” prompt are mutually exclusive signals. The step got shorter.
  • A confirmed review finding can be un-confirmed by a later scope change.A reviewer flagged one line as stale and self-contradicting; it was verified and accepted. The final narrowing then made that same line correct and load-bearing, flipping its acceptance criterion from “must be gone” to “must be present.”
  • Edits to the generated page would have been thrown away.The review tool’s own instructions say to edit the rendered HTML directly. In this project the source file is authoritative and the next render overwrites that HTML, so the edits went to the source instead.

Open items

Known inconsistency, committed as-is. One appendix of the proposal still describes the old “not yet” behaviour that step 7 of the plan overrides. The plan says so explicitly; the proposal was never corrected.

  • The plan is unimplemented.Status todo, twelve steps, nothing applied.
  • Whether to pin the effort level alongside the model.Documented as behaving identically, but no failure has actually been observed from it.
  • Whether the ten-prompt floor justifies revisiting the delegation approach.A chained run crosses roughly ten interactive prompts. Reducing that needs flags on neighbouring skills; captured as a ready-to-paste follow-up.
  • What “inherit” actually re-reads.The session’s model, or the turn’s current override. Sidestepped by pinning explicitly.
  • Rebuilding a source file from a legacy generated-only plan.Deliberately left stopping; captured as a follow-up.

Glossary

Skill
An instruction file the coding assistant loads on demand — either when you type its command, or when what you asked for matches its description.
Automatic activation
A skill loading because your wording matched it, rather than because you typed its command by name.
Command
Invoking a skill explicitly by name, with arguments you pass to it.
Source and render
The text file is authoritative; the web page beside it is generated from that file and safe to overwrite.
Plan status
One of todo, in-progress, or completed, recorded at the top of the plan.
Acceptance criterion
A short statement that is plainly true or false, describing the result rather than the work.
Objective test
The one test that checks the stated goal was actually achieved, as opposed to testing the pieces.
Major / minor version
Release numbering. Major warns everyone already using the tool that something they rely on has changed.
Re-entrancy
Something being started again while an earlier run of it is still in progress — here, a skill calling a chain that calls back into itself.
Worktree
A second working copy of a repository, checked out to a different branch in its own folder.
