The command

One line, two very different execution paths.

/code-review ultra 382

Ultra is the top effort tier of the /code-review command. Its native form launches a multi-agent cloud review: the branch (or a GitHub PR, when you pass a number like 382) is shipped to a fleet of reviewer agents running remotely. It is user-triggered and billed — Claude cannot launch the cloud run on your behalf from inside a session. The older /ultrareview name is a deprecated alias for the same thing. It needs a git repository; the no-argument form bundles your local branch and doesn't even need a GitHub remote.

When the cloud run can't start — as in this session — the command falls back to a local max-effort review that reproduces the same philosophy with the Agent tool: many independent readers, then adversarial verification, then a sweep for what everyone missed. That fallback is what actually reviewed PR #382, and it's what the rest of this guide dissects.

The one design idea to remember: at max effort the review optimizes for recall — catching every real bug — not precision. A missed bug ships; a false positive costs one verification. So the pipeline generates aggressively and filters afterwards, instead of asking one careful reader to be right the first time.

The pipeline

Four phases: gather, fan out, verify, sweep.

PHASE 0Gather the diff853 lines · 7 files

The review scope is pinned down first: git diff origin/main...HEAD, exported to one file every agent reads. For PR #382 that was the humanized plan-skeleton change — an HTML template, a skill spec, an extractor library, a new smoke test, and version metadata.

▼
PHASE 1Fan out 10 finder anglesup to 8 candidates each

Ten agents read the same diff in parallel, each through a different lens (listed below). They are deliberately blind to each other — if two angles flag the same line for different reasons, both records survive. Duplicates are a feature: five independent angles converging on one line is itself evidence.

▼
PHASE 2Dedupe, then verify each survivor1 vote · 3 states

Candidates pointing at the same mechanism are merged, keeping the most concrete failure scenario. Each survivor then gets one verification pass against the actual code — not the diff, the files — and lands in one of three states: CONFIRMED, PLAUSIBLE, or REFUTED. Only REFUTED kills a finding at this effort level.

▼
PHASE 3Sweep for gaps1 fresh reviewer

A final agent gets the verified list and one job: find defects not on it. Fresh eyes plus the list of what's already known is a strong prior for what the first pass tends to miss. On #382 the sweeper found four new issues — including the best copy bug of the whole review.

The ten angles, and what each one caught on #382

  • A · Line-by-line scan 3 foundReads every hunk plus its enclosing function. Caught the fragile extractor regex and a half-applied navigation rename.
  • B · Removed-behavior audit 2 foundFor every deleted line: what invariant did it enforce, and where is it re-established? Caught the File/Path rows losing their always-visible placement.
  • C · Cross-file tracer 2 foundFollows every changed symbol to its consumers. Cleared the galleries, hooks, and finalize flow as safe — and confirmed the extractor gaps.
  • D · Language pitfalls 4 foundHunts the classic traps of each language in the diff. Caught a set -e abort path in the new bash test and the heading-outline problem.
  • E · Wrapper correctness 3 foundWhen code wraps or restructures a mechanism, checks every route still lands. Verified all copy handlers and scroll-spy survived the drawer regroup.
  • Reuse 1 foundFlags new code that re-implements something the codebase has. Caught a CSS rule duplicating an existing label style six declarations out of seven.
  • Simplification 4 foundHunts redundant state and dead code. Caught print rules made unreachable by the regroup and a rule stated three times in the skill spec.
  • Efficiency 0 foundHunts wasted work. Checked the new regexes for catastrophic backtracking on 100 KB plan files — clean, and said so instead of padding.
  • Altitude 4 foundAsks whether each fix sits at the right depth or is a band-aid on shared infrastructure. Caught the four-copies-of-one-heading drift risk.
  • Conventions 0 foundReads every CLAUDE.md governing the changed paths and flags only quotable rule violations. Verified the version bump and changelog were right.

The three verdicts

CONFIRMED

The verifier can name the inputs or state that trigger the bug and quote the failing line. Ships in the report.

PLAUSIBLE

The mechanism is real but the trigger is uncertain — timing, environment, a generator's future behavior. Ships too: this is recall mode.

REFUTED

The code doesn't say that, or a guard elsewhere covers it — proven with a quoted line. Dropped.

Verification is where the pipeline earns its keep. Three plausible-sounding candidates on #382 died here: a claimed false-pass in the new test (refuted — the test's chunking bounds the search correctly), a CSS coupling complaint (refuted — the plan explicitly mandated that selector reuse), and a "missing sections" claim against the markdown skeleton (refuted — the gap predates the PR). All three would have read as legitimate findings in a single-pass review.

Fixes worth a closer look

  • Findings 1 and 3 were proven, not just patched. After loosening the regex and adding the nested-block guard, a functional check fed the extractor a deliberately-drifted plan — extra attributes on the intro, a glance block nested inside the objective — and asserted the output stayed pure.
  • Finding 7 got a mechanism, not just a rename. The smoke test gained a new check that walks every sidebar link and asserts its label equals the target section's heading text — so the four-copy drift class of bug now fails CI instead of shipping.
  • Finding 9 shows the review respecting frozen contracts. Before deleting "dead" CSS, the pipeline grepped the existing test suite and discovered one of those rules is pinned byte-for-byte by test-goal-prompt.sh. The cleanup adapted to reality instead of breaking a passing test.

Running it yourself

Three effort tiers, one command.

# cloud multi-agent review of the current branch
/code-review ultra

# cloud review of a specific GitHub PR
/code-review ultra 382

# lighter local tiers — fewer, higher-confidence findings
/code-review            # default effort
/code-review high       # broader coverage, may include uncertain findings

The ultra cloud run must be started by you (it's billed); if it can't launch, the session runs the local max-effort pipeline described above. --fix applies findings to the working tree; --comment posts them as inline PR comments.

Rule of thumb for choosing a tier: default and high for everyday diffs, where a false positive costs more than it's worth; ultra (or the local max-effort fallback) when the change guards a contract other systems depend on — exactly the situation on #382, where one template feeds galleries, hooks, extractors, and a test suite that all grep it byte-for-byte.
